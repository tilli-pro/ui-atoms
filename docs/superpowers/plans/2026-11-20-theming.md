# Extended Theming (1.2.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship an opt-in `./theme` runtime (store, hook, provider, pre-paint script, token overrides) and restructure the stylesheet so consumers choose their own theming selector, with `system`, high-contrast and seeded-theme support.

**Architecture:** Token values move into Tailwind `@utility` blocks in a selector-free `styles/core.css`; `styles.css` becomes the core plus default selector wiring, so its output for existing consumers is unchanged. The runtime treats the DOM attribute as the state: a framework-free store reads it, a `useSyncExternalStore` hook exposes it, and the pre-paint script is generated from the same config object.

**Tech Stack:** Tailwind CSS 4.3 (`@utility`, `@custom-variant`, `@apply`), React 19 (`useSyncExternalStore`), Vitest + Testing Library (jsdom), `@tailwindcss/node` for compile tests.

**Spec:** `docs/superpowers/specs/2026-11-20-theming-design.md`

## Global Constraints

- Base branch: `feat/version-1.1.0` after 1.1.0 is released. Rebase onto `main` first; the dark-variant fix (`&:where([data-theme="dark"], [data-theme="dark"] *)`) must already be in `packages/ui-atoms/src/styles.css`.
- Additive only. `styles.css` must emit the same token declarations for `:root` and `[data-theme="dark"]` as 1.1.0; Task 7 adds two toggle properties and `color-scheme` to those rules and nothing else. No default token value changes.
- No new runtime dependency. `@tailwindcss/node` is a devDependency through the pnpm catalog, pinned to the catalog's `tailwindcss` version (`4.3.5`).
- Shipped code lives in `packages/ui-atoms/src/`; every test lives in `packages/ui-atoms/__tests__/`.
- Files that touch `document`, `window`, hooks or context start with `"use client";`. `src/theme/config.ts` and `src/theme/script.ts` must not, and must be importable on the server.
- Relative imports inside `src/` end in `.js`.
- Never write a test for a playground recipe (`CLAUDE.md`).
- Each task ends green on: `pnpm lint`, `pnpm typecheck`, `pnpm test`.
- Lint runs Biome `2.5.6`; do not bump it (the shared config pins it).
- Run `pnpm changeset` once, in Task 8: one `minor` for `@tilli.dev/ui-atoms`.

## Review Focus

1. **Storage that throws** (Safari private mode, blocked cookies): `setTheme("dark")` must still set the attribute and must not throw. Pinned in Task 3.
2. **A stored value that is not a preference** (`localStorage.theme = "purple"`, or a value written by another library): falls back to `defaultTheme`, does not write `purple` to the DOM. Pinned in Tasks 3 and 4.
3. **`attribute: "class"` on an element that already has classes**: unrelated classes survive every theme change, and exactly one theme class is present. Pinned in Task 3.
4. **Server render and hydration**: importing `./theme` on the server must not touch `document`; the first client render must match the server snapshot. Pinned in Task 5.
5. **Unmounting a token override**: the element's inline custom properties return to exactly what they were, including properties that had a value before the override. Pinned in Task 6.

    }
  }
}
```

export type ThemePreference = "light" | "dark" | "system";
export type ResolvedTheme = "light" | "dark";
export type ContrastPreference = "normal" | "high" | "system";
export type ResolvedContrast = "normal" | "high";
export type ThemeAttribute = "class" | `data-${string}`;
export interface ThemeConfig {
  attribute: ThemeAttribute;                 // default "data-theme"
  contrastAttribute: ThemeAttribute | false; // default "data-contrast"; false disables the axis
  storageKey: string;                        // default "theme"
  contrastStorageKey: string;                // default "contrast"
  defaultTheme: ThemePreference;             // default "system"
  defaultContrast: ContrastPreference;       // default "system"
  /** What is written for each state. Defaults: light, dark, system-light, system-dark. */
  values: Record<"light" | "dark" | "system-light" | "system-dark", string>;
  /** Defaults: normal, high, system-normal, system-high. */
  contrastValues: Record<"normal" | "high" | "system-normal" | "system-high", string>;
  disableTransitionsOnChange: boolean;       // default true
}
export function defineThemeConfig(overrides?: Partial<ThemeConfig>): ThemeConfig;
export function isThemePreference(value: unknown): value is ThemePreference;
export function isContrastPreference(value: unknown): value is ContrastPreference;
```

`defineThemeConfig` merges `values` and `contrastValues` key by key, so overriding one state keeps the others. A consumer theming with `.dark` passes `{ attribute: "class", values: { dark: "dark", "system-dark": "dark", light: "light", "system-light": "light" } }`.

- Produces, from `store.ts` (`"use client"`):

```ts
export interface ThemeState {
  theme: ThemePreference; resolvedTheme: ResolvedTheme;
  contrast: ContrastPreference; resolvedContrast: ResolvedContrast;
}
export interface ThemeStore {
  getSnapshot(): ThemeState;        // referentially stable until something changes
  getServerSnapshot(): ThemeState;  // defaults; resolved as light / normal
  subscribe(listener: () => void): () => void;
  setTheme(theme: ThemePreference): void;
  setContrast(contrast: ContrastPreference): void;
}
export function createThemeStore(config?: Partial<ThemeConfig>, target?: () => HTMLElement): ThemeStore;
export const defaultThemeStore: ThemeStore;
```

`target` defaults to `() => document.documentElement` and is called lazily, never at creation. The preference comes from storage (falling back to the default); the resolved value comes from the attribute when it holds a known value, otherwise from `matchMedia`.
